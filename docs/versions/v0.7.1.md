## Summary

Follow-up performance release. Two combined refactors — property-path split caching (Option A) and collection capacity hints (Option D) — applied across the 20 actions that walk a property path in a per-row hot loop or dedupe/group into a preallocatable collection. No new Server Actions, no interface changes, no dependency bumps. 986 tests pass on both platforms.

Every optimised action improved 3–24 % vs v0.7.0 on the 20 000-element worst-case scenario. Cumulative improvement vs the v0.6.0 baseline now ranges from 39 % to 73 % across the family.

## Added

- **`--worst-only` flag on `tools/LoadTest`** — skips the Normal scenario and runs only the Worst-case one. Cuts a full perf run from ~35–45 min to ~15–20 min for focused iteration on the actions whose bottleneck is worst-case behaviour.

## Changed

- **Property-path split caching** — a new `SplitPath(string?)` helper splits a dotted property path once per action call. A new pre-split overload `GetPropertyValue(JsonNode, string[]?)` walks the cached segment array without allocating per row. Applied to every action that reads a property inside a per-row hot loop: `List_MinBy`, `List_MaxBy`, `List_Aggregate`, `List_PopByCondition`, `List_PopMultipleByCondition`, `List_Partition`, `List_DistinctBy`, `List_GroupBy`, `List_ZipGroupBy`, `List_Difference`, `List_Intersect`, `List_Union`, and `List_ZipManyGroupBy` (ODC) plus their `Mss*` (O11) mirrors. Output unchanged; the original `GetPropertyValue(JsonNode, string)` remains for callers outside hot loops.
- **Multi-condition compilation** — a new `CompiledCondition` struct + `CompileConditions(List<Condition>?)` helper pre-splits every `Condition.Path` once per action call. A new `EvaluateConditions(JsonNode, CompiledCondition[]?, string)` overload consumes the compiled array. Applied to `List_PopByConditions`, `List_PopMultipleByConditions`, `List_PartitionByConditions`, and `List_ReplaceWhere` (ODC) plus their `Mss*` (O11) mirrors. Behaviour identical (AND/OR short-circuit, `useOr` resolution, per-condition case-sensitivity preserved).
- **Multi-key composite key compilation** — a new `BuildCompositeKey(JsonNode, string[]?[])` overload plus `CompileKeyPaths(List<string>?)` helper pre-split every entry in a list of key paths once. Applied to `List_GroupByMultiple`, `List_ZipGroupByMultiple` (in the `Consume` local function so it compiles once per input list), and `List_ZipManyGroupByMultiple` (compiles a `string[]?[]` per `listIdx` reused for every row on that list). The original `BuildCompositeKey(JsonNode, List<string>)` overload remains.
- **Collection capacity hints** — `Dictionary<string, JsonArray>(array.Count, comparer)` on the `groups` bucket in `List_GroupBy`; `HashSet<string>(picked.Length, comparer)` on the `seen` set in `List_DistinctBy` and `HashSet<string>(arrA.Count + arrB.Count, comparer)` on the `seen` set in `List_Union` (ODC only — net48 lacks the `HashSet<T>(int, IEqualityComparer<T>)` constructor); `List<string>(arrB.Count)` for the B-side key list in `List_Difference` and `List_Intersect` (both platforms). Reduces resize thrash in the ingest loops of grouping / set-op / dedup actions.

## Implementation

### Path-cache flow

Before (per row):

```csharp
foreach (var item in DrainToArray(arrA))
{
    var key = GetPropertyValue(item, MatchKey); // Split("Meta.City") every row
    …
}
```

After (per action call):

```csharp
var segments = SplitPath(MatchKey);       // ["Meta","City"] — allocated once
foreach (var item in DrainToArray(arrA))
{
    var key = GetPropertyValue(item, segments); // no Split, no allocation
    …
}
```

At 20 000 rows per call this saves 20 000 `string.Split(char)` allocations per action. In grouping and set-op actions where two lists are walked, this compounds: `List_Union` on 40 000 combined rows saves ~40 000 splits per call.

For multi-condition actions and multi-key groupers, the pattern extends to arrays of pre-split paths:

```csharp
var compiled = CompileConditions(Conditions);      // once
foreach (var item in DrainToArray(array))
{
    if (EvaluateConditions(item, compiled, LogicalOperator)) …
}
```

### Capacity hint flow

Before: `new Dictionary<string, JsonArray>(comparer)` starts with 3 buckets and grows via `Resize()` at ~5–10 growth points during a 20 000-row ingest.

After: `new Dictionary<string, JsonArray>(array.Count, comparer)` sizes the hash table for the upper bound once, eliminating resize thrash. Same idea for the `HashSet<string>(seenCount, cmp)` in `DistinctBy` / `Union` and the `List<string>(arrB.Count)` for `bValues` in `Difference` / `Intersect`.

### O11 caveats

The `HashSet<T>(int capacity, IEqualityComparer<T> comparer)` constructor is .NET 5+, absent in `net48`. On the O11 target the `DistinctBy` and `Union` seen-set capacity hints are omitted; the default constructor is used. `Dictionary`, `List<T>`, and the path-cache refactor apply to both platforms identically.
