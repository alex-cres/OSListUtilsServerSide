# O11 5,000-Element Dashboard Timings — ListUtils — 2026-10-29

## Scope

Change the O11 dashboard to run every ListUtils action against deterministic 5,000-element
inputs and show per-action timings.

## Data

| Dataset | Shape |
|---------|-------|
| People | 5,000 objects: `Id`, `Name`, `Dept`, `Age`; Dept cycles HR, Ops, Sales, Finance, IT |
| Customers A | 5,000 objects: Id 1–5,000 |
| Customers B | 5,000 objects: Id 2,501–7,500 |
| Orders | 5,000 objects: `OrderId`, `CustId`; customers 1–2,500 have two orders each |
| Numbers | 5,000 integers: 1–5,000 |
| Chunks | 50 Text items, each with 100 integers |

Conditions, key names, and other parameter lists stay small; every data list has 5,000
elements.

## Measurement method

- **Server ms:** SQL Server `SYSUTCDATETIME()` is read immediately before and after the
  ListUtils extension call. Data generation, input parsing, and fingerprinting are excluded.
- **Browser ms:** `performance.now()` around each dashboard call to a test action. Includes
  server-side data generation, OutSystems request handling, network, and the ListUtils call.
- **Correctness:** each output is compared using a fingerprint: total length, the first 80
  characters, and the last 80 characters. This keeps hundreds of KB of output out of the
  browser.
- **Expected fingerprints:** generated by the local `ListUtils.O11` implementation from the
  same deterministic data formulas.

## Caveats

- The server clock on this environment advances in steps of about 15–16 ms. `0 ms` means the
  call finished within one clock tick, not that it took no time. Treat values as coarse buckets;
  repeated runs give better comparisons.
- The first run after publish included warm-up; `List_Pop` measured 297 ms on that run and 31 ms
  on the warm rerun.
- Browser timings are dominated by data generation and request overhead, not the ListUtils call.
